# 6.8.1 联机旧存档兼容性与续档设备切换

日期：2026-11-10。基于 `4fed9d9` 的修复验证，供 6.8.2 发布使用；下列运行发生在更新包版本元数据之前。

## 已验证缺陷与修改

原始 6.8.1 的 `_ensure_client_device_for_saved_seat()` 在没有当前进程历史时，将键盘放在已连接手柄之前。客户端重启后恢复两个保存的席位，即使已连接两个手柄，第二个席位也会自动绑定键盘。旧角色归属正常，但第二个手柄不能移动原来的玩家。

修复只调整候选设备优先级：保留当前进程已有选择；否则优先未被使用的已连接手柄，最后回退到键盘。没有修改存档结构、身份记录、网络协议或热插拔恢复。

续档需要保持的是角色及席位身份，并非保存时的物理设备。测试分别按**本次接入**的双手柄（pads）或单手柄加键盘（mixed）预期设备，向预期设备注入输入，不能从程序实际绑定结果反推测试输入，否则会掩盖绑定错误。

## 测试方式

- 使用两个独立游戏引擎进程、生产 ENet/LAN（localhost:59128），主客各两个本地玩家。不是单机四人存档，也不是模拟网络消息。
- 保存阶段部署原始 Online Friends **6.8.1** ZIP 中的生产脚本；同时加载原始 FiveItemShop **1.1.3**、NoobsWantToLive **1.1.0**。后两者的 11 / 12 个 GDScript 已逐文件核对与发布包字节相同。
- 测试工具 Local-InputProbe 只关闭 Steam 开房，使同一台电脑的独立进程可以运行真实 ENet；不替代存档、身份、菜单、输入或传输逻辑。
- 四份保存阶段都经过真实联机加入与席位分配。之后测试预设四个不同 Noobs 角色和可辨认的装备、金钱、等级、经验、波次，再进入原版合作商店，由原版保存入口和 Online 身份保存钩子实际写盘。没有声称人工打完前七波。
- 完全退出主客进程后，换当前修复源码。每次续档均复制对应原始存档及身份文件到新的隔离用户目录；不会用前一轮续档生成的文件继续测试。
- 主机触发标题页真实“继续游戏”按钮；客户端从标题页加入新开的 LAN 房间，通过生产身份握手恢复席位。续档阶段不注入 RunData、阵容或身份。
- 比较角色 ID、武器 ID（含阶级）、道具 ID 与重复数量、金钱、等级、经验、波次、难度和区域；主机额外比较 run_id、slot_id、owner 等完整身份元数据。
- 通过真实商店开始握手进入下一波（7 → 8），主客各自检查四个玩家节点、本机席位，再依次向 P1—P4 的本次设备发送摇杆轴/键盘事件。两端均验证目标玩家移动、其他三人不动。此短暂移动检查关闭敌人生成，避免受击或追踪移动干扰。
- 引擎为 `3.7.dev.custom_build.74e86be54`，恢复的游戏工程 1.2.0.1；测试进程的 APPDATA 均位于隔离证据目录，不接触日常游戏存档。

## 设备组合矩阵

每端第一个本地席位使用手柄 A；第二个席位根据当次配置使用手柄 B 或键盘。mixed 时仅模拟接入一个手柄，pads 时模拟接入两个手柄。该测试不覆盖同时连接两个手柄却主动选择键盘作为第二输入的情况，也不证明两只实体手柄交换 USB 编号后能按硬件身份追踪同一个人。

矩阵运行：`tests/Test-SaveCompatibility.ps1 -Matrix`。四种保存组合分别用四种当前配置续档，共 16 条路径；其中 12 条改变了至少一端的设备组合。

## 对照与失败保留

同一证据根目录下，修复设备候选排序之前的有效对照：

- `save-compat-keyboard-baseline-20261110-122426`：原始 6.8.1 保存并用原始 6.8.1 续档。角色、装备、进度和身份一致；客户端 P4 被绑定键盘，向原来的第二个手柄注入输入不能移动 P4，两端都观测到该失败。
- `save-compat-keyboard-fixed-20261110-122505` 与 `save-compat-pads-fixed-20261110-122544`：此前仅包含选人初始化及输入隔离修复的源码，同样暴露续档设备问题。
- 候选排序修复后，`save-compat-keyboard-fixed-20261110-122759`、`save-compat-pads-fixed-20261110-122838`、`save-compat-client_keyboard-fixed-20261110-122917` 分别 62 条断言全部通过。这些只验证前后同配置；后续矩阵才验证跨配置切换。

更早的夹具开发失败也保留：错误资源路径、JSON 嵌套结构直接比较、仅注入 action 而非原始设备事件造成的探针问题，均未被归为产品缺陷。最终采用递归数值比较与原始轴/键事件。

日志可能包含 Steam 未初始化、初始日志文件缺失、LAN 标识转数值以及退出资源清理信息；不以“零 ERROR 日志”描述结果。通过阶段要求无 `SCRIPT ERROR`、两个进程正常退出且所有断言通过。

## 重新联机操作

1. 主客双方使用相同的修复版及相同伴随 Mod，先接好本次准备使用的设备。
2. 原主机点“继续游戏”，在合作续档/等待归属界面恢复自己的本地玩家并等待客户端。
3. 客户端从主菜单加入主机新开的房间；不需要点客户端自己的“继续游戏”。LAN 可用房间列表或 IP 直连；Steam 可通过 Mod 加入大厅或主机邀请，Steam 路径仍需跨机器验收。
4. 保留原来的身份配置，正常识别后应恢复各自的旧角色。身份丢失、换电脑或换账号后的人工归属流程不属于这次自动恢复测试。

## 仍需实体设备验收

- 两台电脑上重复四种保存配置与四种续档配置，验证实际 A 键、方向键、摇杆、键盘与 Steam Input。
- 两只同型号手柄、不同 USB 接口/连接顺序、断开重连后的设备编号变化。用户报告的短断连后 P2/P3 互换尚未用真实硬件定位，未作推测性修改。
- 不假设续档沿用旧硬件；人工测试应切换设备组合，并确认本人仍拿回正确角色。引擎事件模拟不能证明实体 HID 枚举行为。
- Steam 跨机器重新开房/加入、整波战斗与完整对局。当前通过范围是本机 ENet、读档进入商店及下一波的短时控制验证。

当前源码的选人、选武器及加入顺序回归另外 **414 条断言全部通过**，新证据及覆盖范围见 [选人输入验证报告](selection-input-validation.md)。功能修复限于三个 Online 脚本；6.8.2 打包另更新 protocol.gd 的包版本常量（网络协议不变）与发布元数据。未提交 Git。
